## 一、订单进度点查 `queryOrderProgressTool` 详细设计

### 1.1 `execute` 算法流程

**初始化阶段**
1. `checkPermission("query_order_progress", params)`，未通过直接返回 `{error: reason}`。
2. 解构 `{ order_no, base }`，读取 `getCurrentUser()?.allowedBusinessTypes`。

**核心逻辑（三路分支）**
1. **指定 base**：
   - 若 `allowed` 存在且不含 `base` → 返回「本助手不支持业务范围」+ 可用清单。
   - `queryOrderProgress(order_no, base)` → 命中返回结果。
   - 主表未命中 → 降级 `queryPendingOrder(order_no)` 查登记表 → 命中返回 `status:"待排产"`。
   - 仍无 → 返回错误 + 提示（单号有误 / 审批未走完 / 超 3 个月窗口 / 试其他业务范围）。
2. **未指定 base**：`queryOrderProgressMany(order_no, basesToQuery)` 并行查全部（`basesToQuery = allowed ?? ALL_BASE_NAMES`）。
   - 命中≥1 → 返回 `matches[]`（多命中附 note）。
   - 全未命中 → 降级登记表 → 再无则返回错误 + hints。
3. **异常（SQL 连接/查询失败）**：返回 `{error:"SQL Server 查询失败", detail, fallback, mock:getOrderInfo(order_no)}`（对话场景降级 mock）。

## 二、订单列表查询 `queryOrdersListTool` 详细设计

### 2.1 `execute` 流程

1. 权限检查。
2. 日期校验：`since`/`until` 须匹配 `YYYY-MM-DD`；`since <= until`。
3. `resolveBusinessTypes(business_types)` 别名展开，未知别名抛错返回可用清单。
4. 业务范围钳制：`allowed` 存在时过滤 `types`，过滤后为空返回提示。
5. 无任何过滤条件 → 默认近 90 天窗口（`effSince`），避免全表扫描。
6. `queryOrdersList({types, ...})` → 结果分拣：
   - `total===0` → 返回未找到 + 过滤条件 + hints/跳过项。
   - 否则返回 `filters_applied` / `default_window` / `total` / `by_type`（真实统计）/ `by_line`（`mergeByLine` 跨类型合并）/ `results` / `truncated_note` / hint。
7. SQL 失败 → 返回 `{error:"SQL Server 查询失败", detail}`（列表查询**无 mock 降级**）。

### 2.2 `queryOneTypeForList` 算法（数据层核心）

1. 固定基地类型 + 请求基地不符 → 跳过不发 SQL，返回 `skipped`。
2. 并行三路：`buildOrderListQuery`（明细 TOP @limit）、`buildOrderListCountQuery`（COUNT DISTINCT 总数/已完成）、`buildOrderListLineCountQuery`（GROUP BY 产品线）。
3. 明细行：`normalizeRowDates` → 异常标记 `exceptions[]`（`isExceptionFlag`）。
4. 上海工艺实验 → `aggregateOrderLots` 按订单聚合；其余 → 按订单号去重。

## 三、权限检查 `checkPermission` 详细设计

分支顺序（Step 0→4）：
1. **Step 0 未认证**：`requireCurrentUser()` 无用户抛错。
2. **Step 1 硬拦截**：`toolName` 前缀命中 `DENY_ALWAYS`（update_/delete_/write_/modify_/execute_sql/run_command）→ 拒。
3. **Step 2 白名单**：`TOOL_PERMISSIONS[toolName]` 不存在 → 仅 supervisor 放行。
4. **Step 3 角色**：`allowRoles.includes(user.role)` 否则拒。
5. **Step 4 参数约束**：`paramCheck(user,args)`，计划岗（planner+baseId）只允许本基地。

## 四、模型额度降级 `runPromptWithModelFallback` 详细设计

### 4.1 `executeTurn` 分支

1. 订阅原始事件；`suppressed=false; errorMessage=null`。
2. `message_end` 且 `stopReason==="error"` → `suppressed=true`、暂存 `errorMessage`、return（不转发）。
3. 其余事件 `onEvent(raw)` 转发；`suppressed` 后一切事件吞掉。
4. `runWithUser(user, ()=>session.prompt(text))` 完成后：
   - 未 suppressed → `{status:"ok"}`。
   - suppressed 且 `isQuota(errorMessage)` → `{status:"quota"}`。
   - 否则 → `{status:"error", message}`。

### 4.2 主循环分支

1. 遍历 `modelChain`，`session.model.id !== target.id` 时 `setModel(target)`。
2. `executeTurn` → `ok` 返回；`error` 立即返回；`quota` 切下一个模型（`console.warn`）。
3. 全部用尽 → `{status:"error", message: "当前模型额度全部用尽…"}`。

### 4.3 额度错误识别正则

匹配 quota/exhausted/insufficient balance/arrears/欠费/(额度|配额)不足/余额不足/未开通/免费额度/trial ended 等；不匹配上下文过长、工具报错。

## 五、日期归一化 `formatSqlDatetime` 详细设计

1. `Date` 实例：`getTime()` NaN → null；`getUTCFullYear()<=1900` → null（哨兵）；否则按 UTC 分量格式化为 `YYYY-MM-DD HH:mm`（还原库中北京墙钟，避免时区换算差 8 小时）。
2. `string`：trim 空 → null；`/^(0000|1899|1900)-/` 哨兵 → null；否则原样返回。
3. 其他 → null。

`normalizeRowDates(row)`：遍历字段，`Date` 实例或 `TIME_FIELD_KEYS` 白名单（VARCHAR 时间列）→ 走 `formatSqlDatetime`。

## 六、工序语义装饰 `decorateProgressRow` 详细设计

1. `STAGE_SPECS[type]` 生成 `stages[]`（node/person/time/done，`done = time !== null`）。
2. `done = row[COMPLETE_KEY[type]] != null`（小试=注塑完成时间、OA=injection_strip_time、其余=final_complete_time）。
3. `current_stage`：
   - 完成 → null。
   - 生产中 → 最后一个 done 工序的下一步；无任何记录 → 第一个做工节点。
4. 返回 `{...row, stages, status, current_stage, current_stage_person}`。

## 七、上海料次聚合 `aggregateOrderLots` 详细设计

1. 按 `order_no` 分组。
2. 每组取 `order_count` 最大者为 `lastLot`（整单完成以最后料次为准）。
3. `lotCompleted` = 状态为「已完成」的料次数；`exceptions` = 各料次并集去重。
4. 输出 `{...lastLot, exceptions, lot_total, lot_completed}`。

## 八、SSE 事件处理链路

`chat.ts` 的 `onEvent`：
1. `tracer.record(raw, traceId)` 落人事记录。
2. `transformAgentEvent(raw)` → SSE 事件（text_delta/thinking_delta/tool_start/tool_end/done/error）。
3. `agent_end` 且未发页脚 → 先补 `text_delta`（`REPLY_FOOTER`）再推 done（页脚仅发前端不写历史，幂等）。
4. `runPromptWithModelFallback` 返回 `error` → 推 `error` 事件。

前端 `ai-client.ts` 按 `\n\n` 分帧，`event:`/`data:` 解析，分发到回调；首次 `X-Session-Id` 头回调 `onSessionId`。

## 九、MaxKB 会话与 scope 路由

1. `buildPromptFromMessages`：忽略 system，user/assistant 历史 `用户：`/`助手：` 前缀拼接；历史助手消息 `stripReplyFooter` 剥页脚。
2. `resolveScopeByModel(body.model)` → scope（all/gz-sample/main）。
3. `maxkbUser = {role:"supervisor", allowedBusinessTypes: scope.types}`；无状态 `sessionId = maxkb-<uuid>`，跑完 `store.delete`。
4. 流式：`chat.completion.chunk` SSE；同步：聚合文本返回 `chat.completion`（usage 全 -1）。

## 十、开放接口状态分拣算法

`GET /open/orders/progress`：
1. `order_no` 必填、长度 ≤64；`base` 别名/逗号解析。
2. `queryOrderProgressMany` 直连数据层（无 mock）。
3. 分拣：`matches`（found 且无 error）/`dbErrors`（有 error）。
4. 状态：`matches≥1`→200；`dbErrors.length===results.length`→500；否则→404。
5. 审计 `logOpenApiEvent` 落盘 JSONL。

## 十一、关键复杂度说明

| 算法/函数 | 时间复杂度/要点 |
|-----------|----------------|
| `queryOrderProgressMany` | O(5) 并行，`Promise.all` |
| `queryOrdersList` | O(types) 并行，每类型 3 路 SQL |
| `aggregateOrderLots` | O(n) 单遍分组（Map） |
| `mergeByLine` | O(n·m) 汇总后排序 O(k·log k) |
| 模型降级链 | O(链长) 最坏重跑 N 次 |
